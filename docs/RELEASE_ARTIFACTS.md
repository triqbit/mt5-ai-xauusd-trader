# MT5 AI/ML Trading Bot - Release Artifact Standards
# Standardized Deployable Artifact Definition (v1.0.0)

This document establishes the authoritative standard for what constitutes a valid, deployable release artifact for the MT5 AI/ML Trading Bot. Compliance with this standard is mandatory for all production deployments.

## 1. Goal
The primary goal of artifact standardization is to ensure that every release is **atomic, traceable, immutable, and verifiable**. An artifact must contain everything required to deploy the system to a clean environment without external dependencies on the build environment.

## 2. Mandatory Artifact Components

Every release package generated by `scripts/package_release.sh` must include the following seven components. The absence of any component renders the release **invalid**.

| Component | File/Format | Purpose |
| :--- | :--- | :--- |
| **Docker Image** | `image.tar.gz` | **Portability**: A compressed tarball of the Docker image, ensuring the exact same binary is used across Staging and Production. |
| **Docker Metadata** | `docker_info.json` | **Traceability**: JSON metadata containing image tag, build timestamp, and the Git SHA for provenance. |
| **Environment Template** | `.env.example` | **Configuration**: The authoritative template for all environment variables required by the specific version. |
| **Database Migrations** | `migrations/` | **Schema Integrity**: The full directory of Alembic migrations required to bring the database to the correct state. |
| **Configuration Docs** | `CONFIG_REFERENCE.md` | **Documentation**: Auto-generated documentation of all Pydantic settings, including types and defaults. |
| **Release Notes** | `RELEASE_NOTES.md` | **Visibility**: Version-specific change log extracted from `CHANGELOG.md` to communicate impact. |
| **Checksum Manifest** | `checksums.sha256` | **Integrity**: SHA256 hashes of all files in the release for tamper-detection and corruption checks. |

## 3. Artifact Directory Structure

Artifacts are stored in a versioned directory within the `releases/` folder:

```text
releases/v<VERSION>/
├── image.tar.gz
├── docker_info.json
├── .env.example
├── CONFIG_REFERENCE.md
├── RELEASE_NOTES.md
├── checksums.sha256
└── migrations/
    ├── env.py
    ├── script.py.mako
    └── versions/
        └── *.py
```

## 4. Standardized Packaging Workflow

The `scripts/package_release.sh` utility enforces this standard through a series of mandatory validation gates:

1.  **Version Synchronization Check**: Verifies that `pyproject.toml`, `src/__init__.py`, and `CHANGELOG.md` share the same version.
2.  **Environment Completeness Check**: Ensures `.env.example` contains all fields defined in the configuration model.
3.  **Migration Reversibility Check**: Performs an upgrade-downgrade-upgrade cycle on a temporary database to ensure schema safety.
4.  **Dependency Harmonization Check**: Confirms that all `requirements*.txt` files use consistent package versions.
5.  **Release Note Verification**: Ensures the `[Unreleased]` or version-specific section in `CHANGELOG.md` is populated.

## 5. Verification Command

Operators must verify the integrity of an artifact before deployment using:

```bash
cd releases/v<VERSION>
sha256sum -c checksums.sha256
```
