# Release Artifact Standards

This document defines what constitutes a valid, deployable artifact for the MT5 AI/ML Trading Bot. Standardizing these artifacts ensures consistency, traceability, and safety across all environments.

> [!IMPORTANT]
> Release artifacts are **build outputs** and should never be committed to the Git repository. They are generated by CI/CD pipelines and stored in secure artifact repositories. The `releases/` directory is ignored by Git via `.gitignore`.

## 1. Mandatory Artifact Components

Every release package generated by `scripts/package_release.sh` must include the following components:

| Component | File/Format | Purpose |
| :--- | :--- | :--- |
| **Docker Image** | `image.tar.gz` | **Offline Portability**: Compressed Docker image for the specific version, ensuring the exact same binary is deployed across environments. |
| **Docker Metadata** | `docker_info.json` | **Traceability**: JSON metadata containing the image name, tag, build timestamp, and Git SHA for provenance. |
| **Environment Template** | `.env.example` | **Configuration Governance**: Authoritative template for environment variables required by this specific version. |
| **Database Migrations** | `migrations/` | **Schema Safety**: Full directory of Alembic migration scripts to ensure database schema alignment. |
| **Configuration Docs** | `CONFIG_REFERENCE.md` | **Operational Clarity**: Auto-generated documentation of all Pydantic settings, types, and default values. |
| **Release Notes** | `RELEASE_NOTES.md` | **Visibility**: Version-specific change log extracted from `CHANGELOG.md` to communicate impact to operators. |
| **Checksum Manifest** | `checksums.sha256` | **Integrity**: SHA256 hashes of all files in the artifact to detect corruption or tampering. |

## 2. Artifact Directory Structure

The packaging process creates a versioned directory under `releases/`:

```text
releases/v<VERSION>/
├── image.tar.gz
├── docker_info.json
├── .env.example
├── CONFIG_REFERENCE.md
├── RELEASE_NOTES.md
├── checksums.sha256
└── migrations/
    ├── env.py
    ├── script.py.mako
    └── versions/
        └── *.py
```

## 3. Automated Validation

The `scripts/package_release.sh` script enforces a strict multi-gate validation process:

1.  **Prerequisite Check**: Verifies that all required Python dependencies (`alembic`, `pydantic`, etc.) are installed.
2.  **Validation Gates**: Executes five mandatory verification scripts:
    - `validate_env.py`: Ensures `.env.example` matches the current configuration schema.
    - `verify_migrations.py`: Confirms database migrations are reversible (Up/Down/Up cycle).
    - `check_release_notes.py`: Ensures `CHANGELOG.md` has descriptive content for the version.
    - `verify_version_sync.py`: Verifies version alignment across `pyproject.toml`, `src/__init__.py`, and `CHANGELOG.md`.
    - `verify_dependencies.py`: Checks for harmonized dependencies across requirements files.
3.  **Artifact Existence**: All seven mandatory components must be present in the target directory.
4.  **Component Integrity**:
    - **Metadata**: Validates that `docker_info.json` is a valid JSON object.
    - **Migrations**: Verifies the presence of the `versions/` directory and migration scripts.
    - **Size**: All generated files must be non-zero in size (detects empty configs or logs).
5.  **Checksum Manifest**: The script generates SHA256 hashes for all files and performs a self-verification (`sha256sum -c checksums.sha256`) after generation.
6.  **Version Consistency**: The artifact directory name (`vX.Y.Z`) must match the `version` field in `pyproject.toml`.

## 4. Deployment and Verification

To verify an artifact before deployment, navigate into the release directory and run the following command:

```bash
# Verify file integrity using the manifest
sha256sum -c checksums.sha256
```

### Expected Output
```text
./image.tar.gz: OK
./docker_info.json: OK
./.env.example: OK
./CONFIG_REFERENCE.md: OK
./RELEASE_NOTES.md: OK
./migrations/env.py: OK
...
```

### Critical Failure Protocol
If any file fails verification (indicated by `FAILED`), the artifact is considered corrupted.
1. **BLOCK DEPLOYMENT**: Do not proceed with the release.
2. **INVESTIGATE**: Check logs from `scripts/package_release.sh` for errors.
3. **REPACKAGE**: Re-run the packaging script once the root cause is resolved.
